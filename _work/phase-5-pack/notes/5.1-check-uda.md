# 5.1 — `check-uda`, and a generalization that was wrong

**Date:** 2026-08-03
**Gate:** 9/9. Preservation: 12/13 in SKILL.md (one phrase intentionally relocated), 8/8 in the reference.
**Sizes:** client 315 + demo 367 → 295 SKILL.md + 90 `references/cloud-remediation.md`. Slots: 2.

## Structure

Near-identical sources (66 diff lines across 682) with the same eight steps. The client project as
base, per the direction doc's guidance to trim the demo's version toward it, plus the demo project's
unique Step 6b.

Split per the doc's "move runbook overlap to docs": the *check* stays in `SKILL.md`; the Cloud

## The finding: I generalized away the thing that made it work

The demo's palette-drift check hardcodes exactly two data types by name. That looked like textbook
project contamination, so I generalized it to *detect all block-editor data types and compare them
pairwise*.

Then I ran it against real `.uda` files — 222 of them — and it found **7 palettes and produced 21
comparisons, of which 18 were nonsense.**

The two hardcoded names weren't contamination. They were the *page-body* palettes. The other five are
**parent-scoped sub-lists**, offered only inside one owning block, which were never meant to be at
parity with anything. The source encoded real knowledge in what looked like a hardcoded value.

**"Make it generic" is not the same as "make it correct."** Nothing in the file said why those two
names were chosen, and the gate could not have caught this — the generalized version was cleaner by
every structural measure and simply produced garbage.

### The fix, and why the heuristic is principled rather than lucky

Palette sizes on the real site are decisively bimodal: **19, 18, 17** for body palettes versus
**1, 1, 1, 1** for sub-lists. A sub-list palette offers exactly one block by construction, since it
exists to constrain one nesting point. So:

> Keep palettes offering more than one block, then compare only pairs sharing at least one block.

That yields exactly the three body palettes and three meaningful comparisons. Plus a
`conventions.md → ## Block palette parity` slot for projects that want to be explicit rather than rely
on inference.

**The corrected version finds more than the original did.** The source compared two palettes; the
heuristic found a third body palette the hardcoded version never looked at, and reported real drift in
it. Every difference it surfaced matches something the project documents as intentional — a grid-only
block that uses areas, and a block whose list home is a different palette.

So generalizing correctly beat hardcoding, but only after the filter was right. Generalizing carelessly
was worse than leaving it alone.

## Method note: my ad-hoc check was worse than the built gate

Verifying slot-fallback consistency by hand, a quick grep reported **2 distinct fallbacks** for
`paths.md → ## Umbraco` — an apparent contract violation. Check 9 said it was fine, and check 9 was
right: my grep compared only the first line of each fallback, and the wrapping differs between files.

Second time this session an ad-hoc verification has been less trustworthy than the checked-in tool.
Worth the discipline: when the gate and a one-off grep disagree, suspect the grep.

# Addendum — first real consumer run found two bugs in the checker

**Date:** 2026-08-03. Source: the canary consumer ran `check-install.sh --verbose` on its trial branch.

The script had only ever been run by its author, in repos its author built. One run in a real project
found two defects, one of them dangerous.

## Bug 1 (dangerous): a name match was counted as a registration

Reported output: `only 2 of 3 reviewer agents are registered`.

The truth: **zero of three toolkit agents were registered.** That project has its *own*
`accessibility-reviewer` and `perf-reviewer` — 11KB regular files, heavily tailored, with their own
calibrated memory. My check tested `-r "$AGENTS_DIR/$name.md"`, found files at those paths, and counted
them as ours.

**The suggested fix was a data-loss path.** As written, `ln -s` would fail on the two existing files.
Add `-f` — which anyone would, seeing it fail — and it replaces 11KB of project-tailored reviewers with
generic skeletons. My own remediation text would have destroyed the exact tailoring the trial exists to
preserve.

Fixed by verifying **identity, not presence**: compare the registered file's content against the
installed copy under `reviewer-discipline/agents/`. That recognizes a symlink and an honest file copy
equally, and recognizes a same-named foreign agent as the distinct situation it is — a **collision**,
which is neither "registered" nor "missing".

The collision message now says plainly that nothing was overwritten, offers the two real choices, and
**explicitly warns against force-linking**. The remediation was more dangerous than the bug.

## Bug 2: an installed pack was invisible

They had installed both pack reference skills. Those aren't in the roster, so the report never mentioned
them, never verified them, and counted `13 of 13` as if core were the whole toolkit — while the pack
slots silently pushed the empty-slot count from 12 to 14. **An unexplained slot count was the only
evidence the pack existed.**

Fixed by splitting the roster into core and pack. Core reports `N of M`; pack reports what is installed;
an *absent* pack is still never a finding, since core-only is the documented baseline.

## What this says about the testing

Both bugs share a root cause: **every fixture was a project I built to exercise a path I had in mind.**
None had a pre-existing agent under a toolkit name, because I never imagined that collision — and
`foreign-units` covered foreign *skills* while missing foreign *agents* entirely, which in hindsight is
an obvious asymmetry.

This is the second time today that running against reality beat structural checking: the palette
generalization was cleaner by every measure and produced garbage, and this checker passed 11 self-built
fixtures while giving dangerous advice to its first real user.

Both new cases now have fixtures (13 total), so neither can regress.
