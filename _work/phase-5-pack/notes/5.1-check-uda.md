## The finding: I generalized away the thing that made it work

The demo's palette-drift check hardcodes exactly two data types by name. That looked like textbook
project contamination, so I generalized it to *detect all block-editor data types and compare them
pairwise*.

Then I ran it against real `.uda` files — 222 of them — and it found **7 palettes and produced 21
comparisons, of which 18 were nonsense.**

The two hardcoded names weren't contamination. They were the *page-body* palettes. The other five are
**parent-scoped sub-lists**, offered only inside one owning block, which were never meant to be at
parity with anything. The source encoded real knowledge in what looked like a hardcoded value.

**"Make it generic" is not the same as "make it correct."** Nothing in the file said why those two
names were chosen, and the gate could not have caught this — the generalized version was cleaner by
every structural measure and simply produced garbage.

### The fix, and why the heuristic is principled rather than lucky

Palette sizes on the real site are decisively bimodal: **19, 18, 17** for body palettes versus
**1, 1, 1, 1** for sub-lists. A sub-list palette offers exactly one block by construction, since it
exists to constrain one nesting point. So:

> Keep palettes offering more than one block, then compare only pairs sharing at least one block.

That yields exactly the three body palettes and three meaningful comparisons. Plus a
`conventions.md → ## Block palette parity` slot for projects that want to be explicit rather than rely
on inference.

**The corrected version finds more than the original did.** The source compared two palettes; the
heuristic found a third body palette the hardcoded version never looked at, and reported real drift in
it. Every difference it surfaced matches something the project documents as intentional — a grid-only
block that uses areas, and a block whose list home is a different palette.

So generalizing correctly beat hardcoding, but only after the filter was right. Generalizing carelessly
was worse than leaving it alone.

## Method note: my ad-hoc check was worse than the built gate

Verifying slot-fallback consistency by hand, a quick grep reported **2 distinct fallbacks** for
`paths.md → ## Umbraco` — an apparent contract violation. Check 9 said it was fine, and check 9 was
right: my grep compared only the first line of each fallback, and the wrapping differs between files.

Second time this session an ad-hoc verification has been less trustworthy than the checked-in tool.
Worth the discipline: when the gate and a one-off grep disagree, suspect the grep.
