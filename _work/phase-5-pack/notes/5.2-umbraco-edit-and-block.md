# 5.2 — `umbraco-edit` and `block`

**Date:** 2026-08-03
**Gate:** 9/9. Preservation: 9/9 and 15/15. Tests: 13/13.
**Sizes:** `umbraco-edit` 84/83 → 122. `block` 115 (demo-only) → 156. Slots: 1 and 4.

## `umbraco-edit` — the client version was better for a reason worth naming

A near-twin (17 diff lines), and every difference was a project fact: two different localhost ports, a
hardcoded agent alias, hardcoded property aliases as examples, a content path.

But the client version wasn't just *cleaner* — it was **more correct**, and in a way that survives
extraction. Where the demo hardcoded `metaName` / `metaDescription` as the example payload, the client
said *"Look up the property aliases — do not assume them"* and *"Look up the agent alias first rather
than hardcoding one — agents are environment-specific."*

That is exactly the discipline a portable spell needs. The client project had already learned, in place,
that hardcoded aliases break across environments — so de-projecting it was mostly a matter of keeping
what it already said. Folded in the reserved-alias facts (`level`, unprefixed generics) since a spell
that tells you to look aliases up should also tell you which ones to avoid choosing.

## `block` — the palette lesson, applied before making the same mistake

5.1 taught that hardcoded values sometimes encode real knowledge. So before stripping `block`'s
apparent contamination, I checked the assumption underneath it.

`block` asserts that views live at a flat `blocks/Components/<alias>.cshtml` path and bind to
`IBlockReference<IPublishedElement, IPublishedElement>`, describing this as "the shared,
editor-agnostic block folder". Measured against both repos:

| | View location | Model directive |
|---|---|---|
| demo project | flat `Views/Partials/blocks/Components/<alias>.cshtml` | `@inherits UmbracoViewPage<IBlockReference<...>>` — all 18 views |
| client project | per-block `Blocks/<Name>/Views/Index.cshtml` in an RCL | `@model <TypedModel>` — generated models, custom view models, `BlockListItem` |

**Two completely different architectures, both valid, and the spell asserted one as though it were the
Umbraco way.** Unlike the palette case, here the hardcoding was *not* encoding hidden knowledge — it
was one project's shape presented as universal. So the right move was the opposite of 5.1's: strip it,
but replace it with discovery rather than with a different assertion.

Step 5 now says **find the closest existing block and follow it exactly** — carry over its model
directive, settings handling, styling approach, and filename convention, because "the existing blocks
are the specification; this spell is not." That is the pointer-first approach the client project's
design-system skill already proves, and it handles both architectures without knowing which it is in.

The instructive pair: 5.1 and 5.2 both involved hardcoded values that looked identical from the
outside. One was load-bearing knowledge and generalizing it produced garbage; one was a false universal
and generalizing it was the fix. **The only way to tell was checking against real repos.** Neither the
gate nor a careful read of the file could have distinguished them.

## What stayed as technology fact

The genuinely Umbraco-general facts all survive in `block`, and they are the reason the spell is worth
shipping at all: `isElement: true` distinguishes an element type; `getByName()` returns `false` not
`null`, so `.toBeNull()` passes on a missing entity and makes the test useless; properties come back
flat, not nested in groups; the dropdown UI alias is `Umb.PropertyEditorUi.Dropdown` and `SelectBox`
does not exist; `level` is reserved; rich text needs `@using Umbraco.Cms.Core.Strings` or the build
fails without pointing at the cause.

## New slot

`stack.md → ## Local URL`, read by `umbraco-edit`, registered as a pack slot keyed to that spell — so a
project that installs only the pack *references* is never asked to fill it. Fallback infers from the
launch profile or `.env`, and asks rather than guessing, because a wrong host fails auth in a way that
looks like a credentials problem.

## Carried forward

- Step 4 (palette registration) tells the agent to identify candidate palettes by looking for data
  types with a `blocks[]` array — the same detection `/check-uda` uses. Untested as an instruction,
  though the detection itself is verified against 222 real `.uda` files.
- `block` is the first pack spell whose correctness depends on an *exemplar existing*. In a greenfield
  Umbraco project with no blocks yet, Step 5 has nothing to copy. The fallback chain degrades to the
  `paths.md → ## Umbraco` slot, but the "copy the closest block" instruction has no answer. Worth
  handling if the pilot starts from zero blocks.
