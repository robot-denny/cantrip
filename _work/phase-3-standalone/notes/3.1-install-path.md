# 3.1 — the install path, and what verifying the CLI changed

**Date:** 2026-08-03
**Gate:** 9/9. **ADR 0004 written**, superseding two claims in ADR 0002.

## Both carried assumptions were wrong

ADR 0002 rested on two findings from the direction doc's 2026-07-30 CLI evaluation and flagged one for
verification here. Against `skills@1.5.21`, **both failed**:

**`--agent` does not install agent definitions.** It selects which *agent tool* to install to —
Claude Code, Cursor, Codex. The doc's "selective pick (`--skill`, `--agent`) works" was true but meant
something else entirely. There is no mechanism in this CLI for installing a registered subagent, so
the three reviewers at repo-root `agents/` would simply have been **absent after any install.**

**There is no `.agents/` tree.** The doc recorded that the CLI "normalizes to canonical
`.agents/skills/` + `.claude/skills/` symlink (our exact convention)". A real install produces only
`.claude/skills/<name>/` as a copied directory. Nothing lands in `.agents/`. The install summary
*prints* an `.agents/skills/` path, which is presumably what made the original reading plausible.

This one had teeth: ADR 0001's "canonical paths" refinement had three spells reading
`.agents/skills/workflow/templates/spec.md` — **a path that does not exist after installation.** The
Phase 1 note recorded replacing the source's `@`-reference with "the canonical install path" as an
improvement. It was an improvement in portability reasoning and wrong on the fact.

Fixed by referencing assets by **skill and asset name** — "the `templates/spec.md` asset of the
`workflow` skill" — never by path. Install layout varies by agent tool and by CLI version, as this
increment demonstrates, so any hardcoded path is a latent break.

## What was right, and one thing nobody had recorded

**Asset bundling works** — installing `workflow` brought both templates along inside the skill
directory. ADR 0002's central decision is verified, which is the one that mattered for
standalone-first.

**Subpath-scoped sources work, and they solve pack selection.** `add <repo>/skills/core` finds exactly
12 skills; `add <repo>/skills/umbraco-17` finds the 2 pack skills. Not in the evaluation at all, and
it delivers "public baseline = core + no pack" with no repo split and no 12-name skill list.

That is a payoff from the Phase 0 taxonomy decision I did not anticipate. `skills/core/` and
`skills/<pack>/` were chosen for legibility and to make invocation posture gate-checkable; they turn
out to be the install-scoping mechanism too. Three benefits from one structural choice.

**The lockfile is richer than expected** — `source`, `sourceType`, `skillPath`, `computedHash` per
skill, with `skillPath` tracking the source location in our taxonomy. So the plan's `toolkit-lock.json`
is dropped: the CLI already writes what the update flow needs, and a parallel lockfile would have to
be kept in sync with the real one for no gain.

## The agents, resolved

Moved to `skills/core/reference/reviewer-discipline/agents/`, so they install and are hash-tracked
like everything else. Registering them in `.claude/agents/` stays a step the CLI cannot perform — one
documented `ln -s` after install.

Standalone-first survives intact because `/code-review` and `/retrofit` **already** documented the
inline-sequential fallback back at 2.3 and 2.5, written then for cross-agent portability. It turns out
to cover this case too: the toolkit is fully functional before the link step, trading concurrency
rather than capability. A degradation written for one reason paid off for another.

## Carried forward

**Treat the doc's CLI evaluation as dated.** Two of its four layout and flag findings did not survive
four days. Its two behavioral findings — that `update` silently clobbers local edits, and that
telemetry uploads file contents — are the load-bearing ones for `/update-toolkit`, and they need their
own verification at 3.2 rather than being trusted. The clobber claim is the entire justification for
building a wrapper, so if it no longer holds, 3.2 gets much smaller.
