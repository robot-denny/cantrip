# 3.2 — `/update-toolkit`

**Date:** 2026-08-03
**Gate:** 9/9.

## The premise verified, unlike the others

I flagged at 3.1 that the doc's CLI findings should be treated as dated, since two of four had already
failed. The clobber claim is the entire justification for building this wrapper, so it got tested
before a line was written:

1. Installed `commit-message` into a scratch project — sha256 `e1a6f821…`
2. Appended a local tailoring — sha256 `289fda42…`
3. Ran `skills update -y`
4. Result: hash back to `e1a6f821…`, the tailoring gone, and the output read **`✓ Updated
   commit-message`**

**Silently clobbered, and reported as success.** The doc's finding holds exactly. This is not merely
unhelpful — it is actively unsafe, because it claims success while destroying work.

## Git is the mechanism, not hashing

My first instinct was pre-flight divergence detection: compare each installed file's hash against the
lockfile's `computedHash` to spot local modifications *before* the update overwrites them. Tested it —
the lockfile hash is **not** a plain digest of the installed file (`3233aba3…` vs the file's
`e1a6f821…`). It is computed over something else, so it cannot serve as a tamper check.

So the design rests on git instead, which turns out to be better anyway:

- **Clean tree required before updating.** After the update, `git diff` is the *only* record of what it
  changed, and pre-existing uncommitted work would be indistinguishable from the update's own edits.
- **Skills must be tracked.** If the install directory is gitignored, there is no net at all — the
  spell says so and requires explicit override.
- **The post-update diff is the review.** A reverted tailoring shows up as the *removal* of content
  upstream never had, which is mechanically distinguishable from a clean upstream change.

Three buckets: clean upstream update, reverted local tailoring, or both — with the last shown as two
separate changes, since the resolution differs for each.

## The reconciliation connects back to the contract

The recommended resolution for a clobbered tailoring is **not** to restore it. It is to move it into
L2, where updates cannot reach. Restoring in place just queues the same loss for next time.

And the spell states plainly that **a tailoring with nowhere to go in L2 is a missing slot, not a user
error** — which is what ADR 0001 already claims, now with a place where a real user hits it and gets
told to report it upstream. The contract rule and the tool that surfaces violations finally meet.

## Two things noted

**Spell count is now 8 + 1.** This is a *maintenance* spell, not a workflow spell — it sits outside the
`explore → … → commit-message` chain entirely. I'm counting it separately rather than quietly calling
the spellbook nine, since the 6–8 guidance is about the workflow set. Flagged for Checkpoint D in case
you read it differently.

**The lockfile drops the subpath.** Installing from `robot-denny/cantrip/skills/core` records
`source: robot-denny/cantrip` — no subpath. That is why update emits `✗ Failed to check for deleted
skills`: it tries to enumerate a source path that no longer matches how the skills were found. The
update itself succeeds, so it is a benign wart, and the spell says so rather than letting a user think
something broke. Worth watching if pack and core installs ever need to be told apart at update time.

## A process bug worth recording: I had defeated my own gate

Committing this increment, the gate reported **1 of 9 failed** and the commit went through anyway.

Cause: I had been invoking it as `./scripts/check-contract.sh | tail -1 && git add -A && git commit`.
A shell pipeline's exit status is the *last* command's, so `&&` was reading `tail`'s success, not the
gate's failure. Every increment from 2.1 onward used that pattern. No damage was done — the gate
happened to pass in all of those — but **the gate had not actually been blocking anything since Phase
1**, and the README's claim that it "runs before every commit" was false.

Two fixes:

- **A `.githooks/pre-commit` hook**, enabled with `core.hooksPath`. A hook cannot be defeated by a
  careless invocation, which is the whole point. Verified by staging a deliberate client-name leak and
  confirming the commit was refused.
- **Stop piping the gate.** Its output is short enough to read whole.

The lesson generalizes past this repo: a check whose result is consumed through a pipeline is a check
you have stopped running, and it fails silently and invisibly in the safe direction until the one time
it matters. Worth remembering that the gate found nine real defects across Phase 2 while, for most of
that phase, being structurally incapable of stopping a commit.

## The check needed an exemption mechanism

The failure itself was a **false positive**: check 8 flagged `npx` in this spell, which legitimately
names the toolkit's own installer. The pattern is dual-use — `npx` in a spell hardcoding a project's
build command is exactly what the check is for.

Rather than weaken the pattern, files can now declare a scoped exemption inline:

```
<!-- contract-allow: npx — reason it is legitimate here -->
```

The reason travels with the exemption so a reviewer can judge it, and it is scoped to the declaring
file and the named pattern only. Negative-tested: with `npx` exempted, `razor` and `umbraco` in the
same file still fail.
