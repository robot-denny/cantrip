# 3.3 — the standalone install, proven

**Date:** 2026-08-03
**Gate:** 9/9.

Two installs from a clean checkout of the pushed repo, into projects the toolkit had never seen.

## Test 1 — empty greenfield repo

`npx skills add robot-denny/cantrip/skills/core --all` → 13 skills installed (12 core + the
maintenance spell). Verified:

- **Canonical layout**: `.agents/skills/<name>/` holds real files; `.claude/skills/<name>` symlinks to
  it.
- **Assets travel**: `workflow/templates/{spec,feature}.md` and
  `reviewer-discipline/agents/{accessibility,code,perf}-reviewer.md` all present.
- **Assets resolve through the symlink** — read `templates/spec.md` via the `.claude/skills/` path
  successfully.
- **No `.agents/config/` exists**, so this install has *every slot empty* — the fresh-install condition
  ADR 0001 names as the acceptance test. Structurally satisfied (check 4 proves every slot reference has
  a fallback); behaviorally untested until a real cast in Phase 4.

## Test 2 — existing project with its own agent

A repo with `package.json`, source, and a pre-existing `.claude/agents/my-existing-agent.md`. After
install and agent-linking:

- **Purely additive** — `git status` showed *no tracked file modified*. Every addition is untracked, so
  the project decides what to commit.
- **The project's own agent survived** alongside the three reviewers.

That is the "works on an existing project" claim, tested rather than asserted.

## The layout finding that corrected my own correction

At 3.1 I recorded that the CLI produces no `.agents/` tree, correcting the direction doc. That was
wrong — or rather, half right. **The layout depends on the invocation:**

| Invocation | Result |
|---|---|
| `--all` (implies `--agent '*'`) | Canonical `.agents/skills/` + `.claude/skills/` symlinks |
| `--agent claude-code` | Copies into `.claude/skills/`, no `.agents/` at all |

My 3.1 probe used a single skill with `--agent claude-code`; the real install command uses `--all`. So
the doc's original claim held for the case that matters, and I over-corrected from one data point —
the same mistake as the Checkpoint B slot hypothesis, two increments after noting the lesson.

It does not change the decision, and in fact strengthens it: **the layout varies by user invocation**,
so referencing assets by skill-and-asset name rather than path is more necessary, not less. But the ADR
now states both behaviors instead of replacing one wrong claim with another.

## Two bugs in my own documentation

**The agent-linking command did not work.** Wrong twice over: it hardcoded `.agents/`, absent under a
single-agent install, and its glob resolved from the shell's directory while a symlink target must be
relative to the *link's* directory. The working form globs through `.claude/skills/` — which exists
under both layouts — and builds each target relative to `.claude/agents/`. Verified in both test
projects.

Worth noting how this was caught: only by running the command I had written, in the environment a user
would run it in. A careful read would not have found either error, because both are about the
relationship between a command and its runtime context rather than anything visible in the text.

**A CLI wart to document, not fix.** The install also creates a top-level `agent/skills/` directory
holding a partial subset of the skills. Unexplained and harmless, but a consumer seeing it will wonder
whether the install broke — so the README says what it is.

## Standalone: achieved

The Phase 3 goal is met. A clean checkout installs into any project, with no host repo, no pack, no
setup skill, and no configuration. Packs are opt-in via subpath. This is the direction doc's "public
baseline = core + no pack", and it is genuinely shippable.

Remaining gap, honestly stated: **installed is not the same as proven to work well.** Every check so
far is structural — files land, paths resolve, nothing is clobbered. Whether the spells produce good
work when cast is Phase 4's question, and nothing before it can answer it.
