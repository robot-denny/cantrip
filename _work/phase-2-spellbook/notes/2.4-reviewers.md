# 2.4 — three reviewer agents + memory discipline

**Date:** 2026-08-03
**Gate:** 8/8 (check 8 extended to cover `agents/`). Preservation: 15/15, 10/10, 12/12.
**Sizes:** 433 source (client base) → 3 agents at 340 total + 2 shared references at 250.

## The duplication was the finding

All three source agents carry the same ~30-line memory-discipline block, the same scope rule, and
the same reporting-balance rules — restated three times, in three slightly different wordings. That
is the exact disease the toolkit exists to cure, sitting inside the assets being extracted.

Split into two shared reference skills the agents defer to:

- **`memory-discipline`** — the MEMORY.md index, topic files, entry format, entry types. Useful to
  any agent with memory, not only reviewers.
- **`reviewer-discipline`** — the diff-only scope rule, the severity scale, the evidence standard,
  the over/under-reporting rules, the report structure.

Each agent is now a thin domain skeleton: an expertise statement, its own checklist, and its
domain's mapping onto the shared scale. The three checklists were always genuinely distinct — that
part was never duplicated.

## Severity: four scales became one

The source had **four different severity scales** across files meant to merge into one report:

| File | Scale |
|---|---|
| `code-review` command | Blocker / Major / Minor / Nit |
| accessibility reviewer | Critical / Major / Minor / Advisory |
| performance reviewer | 🔴 CRITICAL / 🟠 HIGH / 🟡 MEDIUM / 🔵 LOW / ⚪ INFO |
| quality reviewer | 🔴 CRITICAL / 🟠 HIGH / 🟡 MEDIUM / 🔵 LOW |

The orchestrating command named a scale that none of its three reviewers actually emitted. Since
`/code-review`'s job is producing one ordered action plan, this was a live defect, not a cosmetic
one — findings could not be ranked against each other.

Now one scale, defined once in `reviewer-discipline`, with each agent mapping its domain onto it
and an explicit instruction not to invent parallel levels or emoji prefixes. Emoji dropped: they
don't survive merging into a single table.

## The memory taxonomy was already there, unlabeled

The direction doc proposes typing entries as *pattern* / *false-positive-suppression* /
*fixed-with-guard*. Reading the client project's actual memory files shows that taxonomy is
**descriptively accurate to what it organically produced** — the `How to apply:` lines sort cleanly
into "Flag X" (pattern), "Do not flag X" / "Accept X" (suppression), and "Resolved in current code;
if a future change reintroduces it…" (fixed-with-guard).

So formalizing the `type:` field ships a real observed practice rather than an invented scheme.
Two additions the source lacked: an explicit `Type:` line, and a `Recorded:` date (the doc asks for
dating; no source entry had any).

The reference also states plainly that false-positive suppression is the highest-value and
most-skipped type, because a reviewer that repeats a wrong finding gets ignored wholesale.

## Deliberately did NOT pull L1 reviewer rules forward

At 2.1 I wrote the pack skill immediately rather than stubbing it, to avoid re-reading the source.
The same opportunity existed here — the Umbraco reviewer rules were in context — and I declined it.

The distinction: 2.1's pack content was **public technology facts** (MCP tool names, published skill
names). The reviewer rules are **client-harvested** — they carry an agency name inside a service
interface, client assembly names, and project-specific security facts. Checkpoint F exists
specifically to gate harvested content before it reaches a public repo, and pulling it forward would
route around that gate for convenience.

Rule going forward: pull L1 forward when it is public technology fact; defer to 5.4/5.5 when it is
harvested from client work.

## Gate gap found and closed

Check 8 only scanned `skills/core/`, but ADR 0002 puts agents at repo-root `agents/` — they are L0
and equally bound by the no-technology-names rule. A pack adds reviewer rules through the L2
`reviewer-rules/` slot; it never names its technology in the agent. Check 8 now covers both.

## Also removed

The false `Your MEMORY.md is currently empty` boilerplate the direction doc flags as stale — it
asserts a fact about a specific project's state, which is meaningless in a shipped skeleton and
actively wrong the moment memory exists. The hardcoded absolute memory path went the same way; the
memory location is now stated relative to the agent.

## Method: hyphens now fold too

One probe flagged LOST on "thread pool starvation" versus the written "thread-pool starvation".
Compound hyphenation shifts freely while editing and is never what a probe is testing, so the
normalizer now treats hyphens as spaces. Third method fix in three increments — all in verification,
none in extraction.
