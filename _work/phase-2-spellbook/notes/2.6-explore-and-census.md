# 2.6 — `/explore` and the spellbook census

**Date:** 2026-08-03
**Gate:** 9/9. Preservation: 15/15.
**Sizes:** 120 source (demo-only) → 185 L0.

## `/explore`

Demo-only, so no reconciliation. Two changes beyond de-projecting:

**Discovery output moved into the increment bundle.** The source wrote to `docs/discovery/<slug>.md`.
Under §6a the bundle already reserves `_work/<slug>/discovery.md`, so discovery now *opens* the
increment directory that `/spec` and `/plan` then add to. That is a better fit than a parallel
`docs/discovery/` tree, and it means the whole increment archives as one unit including the thinking
that preceded it.

**The PRD pointer changed.** The source seeds `_prds/<slug>.md`; §6a says not to reserve that
directory, so it now points at `docs/`.

The interview mechanics are the substance here and came across intact — one question at a time, walk
the tree branch by branch, look before you ask, and the phase-dependent recommendation policy
(withhold while framing, offer while evaluating) which is the genuinely unusual idea in this spell.

## Census

**8 spells** — `spec`, `plan`, `implement-step`, `feature`, `retrofit`, `explore`, `code-review`,
`commit-message`. Top of the stated 6–8 range, before any pack adds one.

**Chain integrity: clean.**

```
explore → spec → plan → implement-step → feature → code-review → commit-message
                                                         ↑
                                   retrofit (out-of-flow entry) ┘
```

Every spell ends with a `Next:` line. Every `Next:` target exists. No orphans, no dead ends.

**Zero spells invoke other spells.** Audited every imperative reference (`run|invoke|call|execute`
followed by a spell name): three hits, all inside `Next:` lines or describing what *the user* will do.

One nuance worth naming so a future author neither "fixes" it nor accidentally makes it real: a
plan's final step contains the text `Run /feature update <slug>`, and `/implement-step` will dispatch
that step. That looks like invocation-by-proxy, but the human casts `/implement-step N` for each step
individually, so nothing cascades unattended. The plan *records* a suggestion; a human chooses to
execute it. The toolbox property holds — but it holds because of the human in that loop, not by
accident.

**Slot schema: the Checkpoint B hypothesis is disproven.** I flagged then that one slot sufficing for
`/spec` might mean the four-file schema was oversized. With the spellbook complete: **22 slot
references across 18 distinct headings, and all four files are in use.**

| Slot file | Headings in use |
|---|---|
| `conventions.md` | 7 — branch naming, commit format, commit trailers, implementation rules, memory, planning gotchas, unit of work |
| `paths.md` | 4 — workspace, code layout, generated output, umbraco |
| `stack.md` | 3 — build, tests, models |
| `reviewer-rules/` | 3 per-reviewer files plus the shared context |

Well-balanced, and no file is vestigial. The low count at `/spec` reflected that spell's narrow
surface, not an oversized schema. Good outcome for the four-way split from ADR 0001 — and a reminder
to hold a one-data-point hypothesis loosely.

## Open question for Checkpoint C

Eight spells is the ceiling the direction doc set, and the `umbraco-17` pack will add `check-uda`,
`umbraco-edit`, and `block` at Phase 5 — putting a consuming project at eleven. The doc's stated
remedy is a router spell once the count creeps.

My read: don't act yet. A project only ever sees core plus *its* pack, the eight core spells map
cleanly onto distinct workflow stages with no overlap to merge, and the pack's three are
domain-specific enough that a router would add a hop rather than remove confusion. Worth revisiting
after the pack lands and the pilot has cast them in anger — that is real evidence, where a count is
just a number.
