# 5.4 + 5.5 — starter facts and reviewer rules

**Date:** 2026-08-03
**Gate:** 9/9, with check 1 substantially broadened (see Checkpoint F below).
**Output:** 41 facts across 4 topic files, plus `umbraco-17-review-rules`. Pack now 8 units, 27 files.

## 5.4 — the selection criterion is silent failure

Both repos' memory held well over a hundred entries. Most is project architecture and stays L2. The
filter I used for what ships: **does it fail silently?**

Every one of the 41 facts describes something that does not throw, does not warn, and does not appear
in a log — it behaves differently than a reasonable person expects, and the symptom surfaces far from
the cause. An error message you can read is not worth a starter fact.

That criterion produced a much better set than "is it Umbraco-general", which was my first instinct.
Plenty of Umbraco-general facts are self-evident from an error message and add nothing.

The highest-value finds, all of which cost someone real time:

- **A "Default On" toggle returns `false` when never set**, indistinguishable from an explicit false
  using the generated model. Breaks every inheritance chain silently, and the wrong state is the
  default on every untouched page — which is most of them.
- **`$`-referenced AI config keys must be allow-listed, and the refusal is swallowed.** Embeddings stop
  working while the configuration looks correct. Plus the .NET binder merges arrays by index, so
  extending the list without re-listing the defaults *replaces* them.
- **`getByName()` returns `false`, not `null`** — so `.toBeNull()` fails on a missing entity and
  `.toBeFalsy()` *passes*, meaning a test written to prove existence passes against nonexistence.
- **The bulk Deploy "update schema" button reports success without importing.** Its success message is
  the trap; it sends you looking for why the import "did not take."
- **A rebuild API returns 200 having indexed zero documents.**

Every fact carries `Type`, `Applies`, `Verified`, and a `How to apply` — 41/41 complete, verified
mechanically. The format deliberately matches `memory-discipline`'s entry shape, because per §7 these
convert into earned memory once a project confirms them.

Two facts are typed `fixed-with-guard` with narrow version ranges — a serialization bug fixed in a
patch, a beta-only crash. Those are the ones most likely to expire, and the skill says so explicitly
rather than presenting them as durable.

## 5.5 — two findings, one of them a real gap

**The `/plan` routing stub never existed.** The plan called for filling it here, but I wrote the pack
skill complete at 2.1 rather than stubbing it, and the 9-row routing table has been in place since.
Verified rather than assumed — grepped for stub markers and counted the rows.

**The real gap: none of the three agents asked for pack guidance.** They each had their L2
`reviewer-rules/` slot, but nothing in them would ever *find* a pack's review rules — so
`umbraco-17-review-rules` would have shipped and been silently unreachable.

That is an ADR 0003 hole specific to agents. I applied the pattern to `/plan` and `/feature` at 2.1 and
2.2 and did not carry it to the reviewers at 2.4, because at that point no pack review rules existed to
be found. **A mechanism added for one file type does not propagate itself.** All three now ask for a
*kind* of guidance — platform behaviors that fail silently, stack-specific surfaces, version-scoped
facts — while still naming no technology, verified by check 8.

**The review rules defer facts rather than duplicating them.** `umbraco-17-review-rules` says what to
check; `umbraco-17-starter-facts` says why it is true and for which versions. Duplicating 41 facts into
the review rules would have created exactly the divergence one-slot-one-authority exists to prevent.
It also tells reviewers to *cite* the fact, since "this returns empty instead of throwing" is a claim a
reader wants backing for.

## Checkpoint F — the gate was too narrow, and now is not

The manual sweep came back clean on the first pass: nine pattern families across client names, assembly
names, component names, block aliases, domain vocabulary, branch slugs, test artifacts, config values,
and hosts. The only two matches were **the rules that forbid the matches** — `AGENTS.md`'s naming table
and the contract's own checklist.

But a one-off manual sweep is not a gate. Check 1 had been testing six client and agency names, which
was never sufficient: **harvested content identifies its source through assembly names, component
names, block aliases, project config values, branch slugs, and test filenames just as surely as through
a client name.** Any of those would have sailed through.

Check 1 now covers all of it, and both scrub checks share one exemption mechanism — needed because the
documents defining these rules must quote what they forbid. `AGENTS.md` declares
`<!-- contract-allow: department -->` with its reason inline.

Negative-tested by injecting a client assembly name and a project component name into a doc: both
caught, then the repo returns to 9/9.

This is the session's recurring lesson in its sharpest form. The scrub *rule* has existed since Phase 0
and I have leaked a client name three times under it. The rule was never the problem — the gate's
pattern list was, and it stayed narrow until the increment that most needed it forced a wider look.


### Postscript: the broadened gate caught this very note

Writing the paragraph above, I quoted the two terms verbatim as examples of what the negative test
injected — and the gate blocked the commit. Fourth leak of the session, and the first where the leak was
*a description of testing for leaks*.

Not exempted. The note does not need to name them to describe the test, so it now says "a client
assembly name and a project component name". An exemption would have been the lazy fix and would have
punched a permanent hole in the check for the sake of one sentence.

Worth noting the gate is now strict enough that writing *about* the scrub requires care. That is the
correct side to err on for a public repo, but it is a real authoring cost and future notes should expect
it.
