# 6.2 — `design-system-authoring`

**Date:** 2026-08-04
**Gate:** 9/9. Method elements: 11/11. Core spells still 9; references now 5.
**Sizes:** 437 source lines (one project's design-system skill) → 148-line meta-skill + 104-line template.

## What was actually extracted

Per §8, the *content* stays L2 and only the *shape* ships. So this increment read a working
design-system skill and asked: **what is the method here, independent of the system it describes?**

Seven transferable elements, none of which were stated in the source — they had to be inferred from why
it was built that way:

1. **Conformance framing.** The source opens by saying the goal is *not* novel design. That is fighting
   a specific default: an agent asked to build a card will explore an aesthetic unless told there is one
   right answer already in the codebase.
2. **Lead with the load-bearing mechanism.** The source's spine is its theming engine, and the reason it
   leads is that violating it **fails silently** — correct in the default state, broken the moment
   someone switches. Generalized into a test for finding such a mechanism in any project: *if new UI
   ignores it, does anything fail loudly?* If not, that is the spine.
3. **Pointer-first.** "The codebase is the source of truth, not this skill… read them fresh each time
   rather than trusting a remembered snapshot." The reasoning generalizes cleanly: conventions evolve, a
   restatement goes stale invisibly, and **a confidently wrong convention is worse than none because it
   will be followed.**
4. **Exemplar-first.** Copy the two or three closest existing components. This inherits conventions
   nobody wrote down — the highest-leverage instruction in the whole source.
5. **A checkable list.** Generalized into two properties: verifiable from the diff, and naming the
   artifact rather than the intention. Plus the observation that a list derived from *real review
   findings* beats one derived from the system's documentation, because it covers what people get wrong
   rather than what the system intends.
6. **Trigger engineering, with skip conditions.** The source's description is unusually long and
   deliberately catches casual asks. That is the element most likely to be skipped by someone authoring
   their own, and it decides whether the skill ever loads.
7. **Visual verification as the real test.** Switching the mechanism and confirming the UI responds is
   the only thing that catches the Step 1 failure — reading a diff cannot.

## Two judgment calls

**Reference, not spell.** The source is model-invoked, and I kept that posture rather than making the
meta-skill a spell. Three reasons, and the third is decisive: it keeps the core spellbook at 9 rather
than reopening the Checkpoint C count; it is guidance rather than an action; and **the whole problem is
the request that never mentioned design at all.** A user-cast spell only fires when someone remembers to
cast it, which is precisely not the failure case. The skill says this about itself under *What not to
do*, so anyone tempted to convert it sees the reasoning.

**L0, not L1.** §8 assigns this to core, and that is right — generating a design-system skill from a
project's tokens and exemplars needs nothing stack-specific. It did mean stripping every trace of the
source's stack: no framework name, no template language, no icon library, no token syntax, no service
type. Verified zero technology names and zero client vocabulary, which check 8 enforces going forward.

The template carries the structure with each section marked for what to fill, so the generated skill
inherits the shape without inheriting anyone's design system.

## The thing this productizes

The direction doc describes the source skill as "the afternoon" — a focused session that turned an
implicit visual system into something an agent could conform to. What makes it worth productizing is not
the writing, it is knowing **which seven things to put in it**, and in particular that the spine is
whichever mechanism fails silently.

That last point is the transferable insight and it is not obvious. Someone authoring a design-system
skill from scratch would naturally lead with the type scale or the color palette — the things a design
system is *about*. The right thing to lead with is the mechanism whose violation nobody notices.

## Carried forward

- Untested against a project that has **no** established design system. A greenfield project has no
  exemplars to copy and no load-bearing mechanism yet, so Steps 1 and 3 have nothing to work with. The
  honest answer is probably that this skill does not apply until a system exists — worth saying so
  explicitly rather than letting someone generate a skill full of unfilled placeholders.
- Same gap as `/block`'s Step 5, and the same root cause: **an exemplar-first instruction has no answer
  when there is no exemplar.** Two increments have now hit it, which makes it a pattern rather than a
  one-off, and probably something the setup skill should detect at 6.1.
